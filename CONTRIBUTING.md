# CONTRIBUTING

## Назначение

Этот документ описывает только процесс внесения изменений в репозиторий.
Установка и запуск проекта описаны в `README.md`.

## Базовый workflow

1. Создай рабочую ветку от `master`.
2. Внеси изменения.
3. Прогони проверки локально.
4. Сделай commit и push.
5. Открой Merge Request по шаблону `.gitlab/merge_request_templates/default.md`.

## Обязательные проверки

Перед push обязательно:

```bash
make project-check
```

Автоматически:

- `pre-commit` запускается на commit
- `pre-push` запускает:
  - `make type-check`
  - `make test-critical`

Если хук упал, исправь проблему и повтори commit/push.

## Требования к документации и docstring

- Текст документации в репозитории веди на русском языке.
- Для каждого публичного Python-модуля обязателен module docstring.
- Для каждого публичного класса и функции обязателен docstring с кратким описанием.
- Для функций в docstring указывай секции `Args`, `Returns` и `Raises` при наличии соответствующих аргументов, возвращаемого значения и исключений.
- Проверка docstring обязательна в линтере (`ruff` правила `D` с `convention = "google"`).

## Соглашение по commit message

Рекомендуемые типы:

- `feat`: новая функциональность
- `fix`: исправление бага
- `refactor`: рефакторинг без изменения поведения
- `test`: тесты
- `docs`: документация
- `chore`: служебные изменения
- `perf`: оптимизация производительности
- `ci`: изменения CI/CD
- `revert`: откат

Примеры:

- `feat(api): добавил endpoint выдачи токена`
- `fix(auth): исправил обработку истекшего refresh-token`

## Требования к Merge Request

- Используй шаблон MR из `.gitlab/merge_request_templates/default.md`.
- Пиши понятный заголовок и описание: что изменено, зачем, какие риски и как проверять.
- Укажи связанные задачи/ссылки (если есть).

## Архитектурные ограничения (backend)

- `domain` — ядро бизнес-правил. Здесь сущности и доменная логика. Этот слой ни от кого не зависит.
- `application` — сценарии работы системы (use-cases): «что нужно сделать» в бизнес-смысле. Может использовать только `domain`.
- `infrastructure` — техническая реализация: БД, внешние API, файлы, логирование. Подключается к `application` и `domain`.
- `presentation` — слой входа в систему (например, HTTP/FastAPI).
  Он принимает запрос, валидирует данные, вызывает нужный use-case и возвращает ответ.
  Бизнес-логика и прямой доступ к БД здесь не пишутся.
