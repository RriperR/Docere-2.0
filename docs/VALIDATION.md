# Воспроизводимая проверка качества

Этот документ отделяет измеренные результаты от проектных требований. Команды выполняются на конкретном commit и
оставляют исходные артефакты, которые можно приложить к пояснительной записке.

## Программные проверки

| Область | Команда | Что подтверждает |
|---|---|---|
| Backend | `make project-check` | pre-commit, Ruff, форматирование, строгий mypy и pytest |
| Покрытие | `make test-with-coverage` | число backend-тестов и покрытие строк |
| Frontend | `make frontend-check` | production build, ESLint и Vitest |
| Полный пользовательский поток | GitLab job `demo-e2e` | запуск контейнеров, импорт и совместный разбор двумя врачами |

В отчёте следует сохранить commit SHA, версии Python/Node/Docker и полные логи job. Числа из другого commit нельзя
выдавать за результат текущей версии.

## Демонстрационный стенд

**Используйте только отдельную синтетическую базу.** `demo-up` и `demo-reset` очищают прикладные
таблицы выбранного Compose-проекта. Для существующих данных следуйте
[инструкции обновления](DEVELOPMENT.md#обновление-существующего-стенда). Имя проекта выбирается через
`COMPOSE_PROJECT_NAME`; отдельному стенду также нужны свободные порты из Compose-конфигурации.

```bash
make demo-up
make demo-check
```

Стенд состоит из Nginx, React frontend, FastAPI API, Celery worker, независимого dispatcher, PostgreSQL, Redis и MinIO. `make demo-up`
применяет миграции, очищает прикладные таблицы, создаёт синтетические учётные записи и генерирует архив для сценария импорта.

Полезные команды:

```bash
make demo-reset  # вернуть синтетические данные к исходному состоянию
make demo-logs   # показать последние логи прикладных сервисов
make demo-down   # остановить стенд, сохранив volumes
# Только для одноразового стенда: down -v удаляет его PostgreSQL/MinIO volumes.
```

## Нагрузочный эксперимент

После `make demo-up`:

```bash
make benchmark
```

Скрипт выполняет аутентифицированное чтение медицинской истории с частотой 5, 10 и 20 запросов в секунду. Для каждой
серии сохраняются p50, p95, p99, максимум, достигнутая частота и доля ошибок. Исходный JSON находится в
`artifacts/benchmark-results.json` и содержит время измерения, commit SHA и параметры компьютера.

Для более длинной серии:

```bash
uv run python scripts/benchmark_api.py \
  --rates 5 10 20 30 40 \
  --duration 60 \
  --output artifacts/benchmark-results.json
```

Результаты локального стенда характеризуют только указанную конфигурацию. Их нельзя переносить на staging или
production без повторного измерения.

## Проверка импорта

`make demo-up` создаёт `docere-demo-archive.zip` с синтетическими примерами:

- совпадение с существующим пациентом и новая карточка;
- DICOM-группа;
- неоднозначная дата;
- потенциальный дубликат;
- пустой файл и небезопасный ZIP-путь.

Playwright проходит загрузку, review, resolve и переход к созданной записи. Для дипломного эксперимента следует
дополнительно собрать размеченный набор архивов и вычислить precision, recall и F1 для поиска дублей.

## Проверка совместного разбора

Минимальный backend-прогон:

```bash
make test ARGS='tests/critical/test_clinical_cases.py -q'
```

Без PostgreSQL часть конкурентных проверок пропускается. Для полного прогона используйте отдельную
тестовую БД: тесты создают и удаляют только собственные временные схемы. Пользователь должен иметь
права создавать схемы. Не подставляйте URL рабочей базы.

```bash
DOCERE_TEST_POSTGRES_URL=postgresql+psycopg://USER:PASSWORD@HOST/TEST_DB \
  make test ARGS='tests/critical/test_clinical_cases.py tests/integration/test_schema_migrations.py -q'
```

Проверки включают:

- непринятое приглашение без клинического контекста и принятие с актуальными материалами;
- полную проверку ACL, нейтральную карточку, независимые источники и каскадный отзыв;
- блокировку/потерю роли, срок действия исходного права и доступ к предыдущему случаю;
- один уровень ответов, ключ идемпотентности и права на запросы мнения;
- фильтры поиска, сигнатуру файла и соответствие вложения материалу;
- версии итога, закрытие и публикацию без дублей с отдельной датой события;
- сбой брокера, повторную доставку, непрочитанное обсуждение без уведомления на каждую реплику;
- SSE с Bearer-заголовком, истечением токена и повторной проверкой доступа;
- конкурирующие изменения/публикации/доставку на PostgreSQL и полный цикл миграций.

Для UI используйте отдельный demo-стенд с двумя синтетическими врачами. E2E создаёт дополнительные
синтетические записи и третьего врача; не запускайте его на рабочем окружении.

```bash
cd frontend
npm ci
npx playwright install chromium
PLAYWRIGHT_BASE_URL=http://localhost:8000 npm run test:e2e -- clinical-cases.spec.ts
```

Сценарий проходит создание случая, принятие приглашения, обсуждение, запрос мнения, добавление материалов,
просмотр вложения, итог, закрытие и публикацию. Проверяет постороннего врача и отзыв доступа при открытом
документе. Полный набор E2E также требует архив `/fixtures/docere-demo-archive.zip`: его подготовка,
контейнер Playwright и сохранение trace/отчёта описаны в job `demo-e2e` файла [`.gitlab-ci.yml`](../.gitlab-ci.yml).

Контрольные результаты 22 сентября выше относятся к старому commit и не описывают объём текущих проверок.
Новый прогон фиксируйте вместе с SHA и логами; покрытие старой версии не переносите на новый код.

## Восстановление и RTO/RPO

RTO и RPO остаются целями до отдельного эксперимента с согласованной копией PostgreSQL и MinIO. В протоколе
восстановления нужно сохранить время начала и окончания, commit SHA, версии образов, число строк в ключевых таблицах и
контрольные суммы объектов. Такой эксперимент следует проводить в отдельном окружении, не на демонстрационной базе.
