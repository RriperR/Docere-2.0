# Воспроизводимая проверка качества

Этот документ отделяет измеренные результаты от проектных требований. Команды выполняются на конкретном commit и
оставляют исходные артефакты, которые можно приложить к пояснительной записке.

## Программные проверки

| Область | Команда | Что подтверждает |
|---|---|---|
| Backend | `make project-check` | pre-commit, Ruff, форматирование, строгий mypy и pytest |
| Покрытие | `make test-with-coverage` | число backend-тестов и покрытие строк |
| Frontend | `make frontend-check` | production build, ESLint и Vitest |
| Полный пользовательский поток | GitLab job `demo-e2e` | запуск контейнеров и три Playwright-сценария |

В отчёте следует сохранить commit SHA, версии Python/Node/Docker и полные логи job. Числа из другого commit нельзя
выдавать за результат текущей версии.

## Демонстрационный стенд

```bash
make demo-up
make demo-check
```

Стенд состоит из Nginx, React frontend, FastAPI API, Celery worker, PostgreSQL, Redis и MinIO. `make demo-up`
применяет миграции, создаёт только синтетические учётные записи и генерирует архив для сценария импорта.

Полезные команды:

```bash
make demo-reset  # вернуть синтетические данные к исходному состоянию
make demo-logs   # показать последние логи прикладных сервисов
make demo-down   # остановить стенд, сохранив volumes
docker compose down -v  # полностью удалить локальные данные стенда
```

## Нагрузочный эксперимент

После `make demo-up`:

```bash
make benchmark
```

Скрипт выполняет аутентифицированное чтение медицинской истории с частотой 5, 10 и 20 запросов в секунду. Для каждой
серии сохраняются p50, p95, p99, максимум, достигнутая частота и доля ошибок. Исходный JSON находится в
`artifacts/benchmark-results.json` и содержит время измерения, commit SHA и параметры компьютера.

Для более длинной серии:

```bash
uv run python scripts/benchmark_api.py \
  --rates 5 10 20 30 40 \
  --duration 60 \
  --output artifacts/benchmark-results.json
```

Результаты локального стенда характеризуют только указанную конфигурацию. Их нельзя переносить на staging или
production без повторного измерения.

## Проверка импорта

`make demo-up` создаёт `docere-demo-archive.zip` с синтетическими примерами:

- совпадение с существующим пациентом и новая карточка;
- DICOM-группа;
- неоднозначная дата;
- потенциальный дубликат;
- пустой файл и небезопасный ZIP-путь.

Playwright проходит загрузку, review, resolve и переход к созданной записи. Для дипломного эксперимента следует
дополнительно собрать размеченный набор архивов и вычислить precision, recall и F1 для поиска дублей.

## Восстановление и RTO/RPO

RTO и RPO остаются целями до отдельного эксперимента с согласованной копией PostgreSQL и MinIO. В протоколе
восстановления нужно сохранить время начала и окончания, commit SHA, версии образов, число строк в ключевых таблицах и
контрольные суммы объектов. Такой эксперимент следует проводить в отдельном окружении, не на демонстрационной базе.
