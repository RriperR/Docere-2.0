# A1: baseline начала работы

Дата проверки: 12 октября 2026. Область: только A1 из `docs/roadmap/01-onboarding.md`.

## Условия и воспроизведение

Изолированный локальный стенд `http://localhost:8012`, Compose project
`docere-roadmap-a1-20261012`, новая PostgreSQL/S3, миграция `20261011_25`.
Администратор создан штатной командой create-admin; AI выключен.
Первоначально localhost не отвечал; после запуска отдельного окружения `/api/health` отвечает 200.
Выполняется текущий frontend из образа предыдущего этапа `docere-ai-*`.
Ни seed-demo, ни reset, ни SQL для аккаунтов/привязки не применялись.

Тест `frontend/e2e/onboarding.spec.ts` создаёт через публичную UI-регистрацию пять
синтетических аккаунтов с уникальным UUID в email: пациент, ожидающий врач,
первый врач, второй врач и посторонний. Каждый получает отдельный browser context.
Двум врачам роль подтверждается существующим admin API; третья заявка остаётся pending.
UUID карточки, задания и записи берутся из реальных ответов сервера.
Используется существующая синтетическая PNG-фикстура
`tests/fixtures/import_ai/synthetic-scan.png`; реальных медицинских данных нет.

```bash
cd frontend
PLAYWRIGHT_BASE_URL=http://localhost:8012 npx playwright test e2e/onboarding.spec.ts --retries=0 --reporter=list
```

На другом стенде задать `PLAYWRIGHT_BASE_URL`, при необходимости
`ONBOARDING_ADMIN_EMAIL` и `ONBOARDING_ADMIN_PASSWORD`.
Chromium устанавливается через `npx playwright install chromium`.
Тест оставляет свои синтетические данные для изучения; каждый повтор создаёт новые аккаунты.

## Отдельные наблюдения и ограничения

- `.test` проходит клиентскую проверку email, но backend отклоняет регистрацию с техническим
  текстом `body.email: value is not a valid email address... special-use or reserved name`.
  Рабочий сценарий использует уникальные адреса `@example.com`. Условия валидности следует
  объяснять понятным сообщением; production code в A1 не менялся.
- У нового врача есть автоматически созданная собственная карточка. Создать настоящего
  подтверждённого врача с нулём доступных карточек указанным публичным путём не получилось.
  Удаление/перепривязка БД для воспроизведения такого состояния не выполнялись.
- Совпадение email при создании врачом отдельной карточки не следует считать доказательством
  личности. Отдельно проверяется фактический доступ зарегистрированного пациента до sharing.
  Реальный запрос с токеном пациента до приглашения и после отправки, но до принятия,
  возвращает 403. После принятия запись читается без привязки аккаунта к этой карточке.
  Привязка аккаунта к карточке относится к C4; A1 не добавляет такой механизм.
- Полная навигация на `/dashboard/patient` после принятия показывает собственную пустую
  карточку и не показывает принятую запись. Эта проверка пожелания A3 выявила пробел;
  заведомо падающий assertion не оставлен в E2E. Успешный путь использует
  «Открыть карточку» из принятого приглашения.
- Требование о враче буквально без пациентов остаётся ограничением: получен новый врач
  без добавленных им пациентов, но с собственной карточкой. Admin UI, rejected lifecycle,
  мобильная приёмка и мастер случая в этом A1 не проверялись.
