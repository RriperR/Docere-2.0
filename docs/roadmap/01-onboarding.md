## A1 — зафиксировать сценарий нового пользователя

Зависимости: нет. Результат: docs/reviews/onboarding-baseline.md + целевой E2E.

1. Использовать отдельные новые синтетические аккаунты: пациент; пользователь с ожидающей
   заявкой врача; подтверждённый врач без пациентов; второй врач; посторонний.
2. Пройти регистрацию, заявку, одобрение существующим механизмом, первый вход, создание
   карточки, загрузку файла без AI, ручную проверку и открытие записи.
3. Пройти уже поддерживаемую передачу врач → пациент → второй врач.
   Если шаг требует несуществующей привязки аккаунта, записать ограничение для C4;
   не обходить его ручным изменением БД и не добавлять автоматическую привязку.
4. Записать для каждого шага URL, действие, фактический результат, препятствие и ожидаемое
   поведение A2/A3. Не проводить аудит всего репозитория.
5. Добавить E2E существующего успешного пути. Обнаруженные UX-проблемы перечислить отдельно;
   не оставлять заведомо падающие тесты в master.

Приёмка: воспроизводимый отчёт содержит начальные условия и отделяет текущую функциональность
от пожеланий; тест создаёт собственные данные и не зависит от фиксированных UUID.

## A2 — следующий шаг после регистрации и на пустом рабочем столе

Зависимость: A1. Основная область: frontend; API только если действительно не хватает
уже существующего безопасного состояния заявки/счётчика.

- Пациент без заявки видит свою историю и отдельное действие «Я врач» с переходом к заявке.
- Ожидающая заявка: текущий статус и объяснение ожидания; повторную действующую заявку не создавать.
- Отклонённая заявка: показать разрешённую сервером причину/следующее действие согласно
  существующему lifecycle. Не изобретать право повторной подачи, если его нет.
- Подтверждённый врач без пациентов: главное действие «Добавить пациента», второе «Импорт документов».
- Если уже есть входящее приглашение или задача, показывать их штатным компонентом входящих.
- Не создавать отдельную таблицу «онбординг завершён»; состояние выводить из имеющихся данных.
- Состояния загрузки, ошибки с повтором, пустого результата различимы.
- Не отображать кнопки как доступные, если сервер запрещает действие.
- На существующем наполненном рабочем столе сохраняются текущие блоки.

Приёмка: тесты всех состояний заявки; новый врач начинает работу без знания терминов
«паспорт» или UUID; 390/768/1440 px, клавиатура и 200% zoom.
Не менять схему подтверждения роли администратором/двумя врачами.

## A3 — связать пациента, импорт и начало разбора

Зависимость: A2.

- Из карточки пациента добавить/проверить явный переход к загрузке и ручному созданию записи.
- Контекст пациента передавать как ID; перед подстановкой сервер проверяет доступ.
  Ссылка не назначает файлы пациенту автоматически.
- При несовпадении извлечённых данных оставить существующий ручной выбор, предупреждения
  и распределение групп. Не подменять дату рождения датой события.
- После resolve показать созданные записи и прямые ссылки. Для импорта нескольких пациентов
  перечислить результаты по пациентам; не направлять все записи в одну карточку.
- Из выбранных записей предложить существующий мастер случая. Выбор остаётся явным.
- Краткие пояснения: карточка — человек; запись — событие/документ; случай — обсуждение
  выбранных записей. Вставить их в пустые состояния/подсказки, не добавлять длинный тур.
- На пациентском dashboard проверить чтение принятых материалов и передачу зарегистрированному
  врачу через существующее sharing; переход не должен выдавать права до принятия.

Приёмка: E2E «новый врач → карточка → импорт без AI → ручная проверка → запись → мастер случая»,
ошибка сети не теряет review; чужой patient ID отклоняется; AI выключен и сценарий работает.
Для пациента — чтение и передача только разрешённых записей. Неразрешённый вопрос привязки — C4.
