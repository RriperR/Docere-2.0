## B1 — серверные коллекции с пагинацией

Зависимость: A1 (знание сценария). UI пока не мигрировать.

Контракт новой версии коллекций:
- GET /api/patients/page: offset=0, limit=20 (1..100), q необязательный до 255 символов.
- GET /api/patients/{patient_id}/records/page: offset/limit; q; record_type;
  confirmation_status; event_date_from/event_date_to.
- Ответ {items, total, offset, limit}. Существующие item schemas переиспользовать.
- Список пациентов: сортировка fio ASC, id ASC; q — буквальный регистронезависимый
  поиск подстроки ФИО. Спецсимволы SQL LIKE экранировать, использовать bind parameters.
- История: event_date DESC NULLS LAST, created_at DESC, id DESC.
  q ищет в названии, clinical_summary и имени доступного вложения записи.
  Комментарии, PDF-текст и AI-сводки не индексировать.
- Типы/статусы взять из текущих enum. Интервал включителен; from > to — 422.
- Права применяются ДО count/offset/limit. JOIN вложений не дублирует записи;
  использовать EXISTS либо эквивалентный запрос.
- Несуществующий/недоступный пациент — существующая единообразная 404.
- Зарегистрировать /page до динамического /{patient_id}.
- Старые массивные endpoints временно сохранить без изменения shape. Не добавлять к ним
  полиморфный ответ «массив или объект» в зависимости от параметра.
- Не вычислять пагинацию Python-срезом загруженной всей истории. Query и count — в repository.
- Индексы добавлять по проверенному плану PostgreSQL, не по каждому полю вслепую.
- Поисковые значения q могут содержать медицинский текст: не логировать query strings
  в gateway/APM; описание API должно требовать их редактирования/маскирования в логах.

Приёмка: PostgreSQL-тесты пустой/последней/следующей страницы, равных дат,
одной записи с несколькими вложениями, разных прав на записи одного пациента, отзыва,
expired sharing, чужого пациента, invalid filters. total соответствует доступной выборке.

## B2 — перевести потребителей на страницы

Зависимость: B1.

- Перевести PatientListPage, PatientDetailsPage, связанные stores и CaseMaterialPicker
  на новые коллекции. Найти прочих потребителей старых списков через rg и перечислить в отчёте.
- offset, limit, тип, статус, даты и record ID хранить в URL. Свободный q хранить только
  в памяти приложения; восстанавливать на back в пределах сессии, очищать на logout.
  Для запросов отправлять q на сервер; не включать его в клиентскую аналитику.
- Фильтр сбрасывает offset в 0. Debounce поиска 300 ms; отмена предыдущего запроса
  или проверка request ID исключает запоздавшие ответы.
- При открытии record ID вне текущей страницы адресно получить запись, проверив её
  patient_id; не выгружать все страницы ради перехода.
- При недействительном offset после удаления/отзыва перейти на существующую страницу;
  ошибка сети не выглядит пустой историей.
- Счётчики показывают total сервера. Не использовать items.length как размер всей истории.
- Старые API объявить deprecated в документации; не удалять в этом пакете.

Приёмка: возврат назад сохраняет фильтры/страницу; прямой URL открывает нужную запись;
поздний ответ старого поиска игнорируется; смена пользователя очищает список и поиск;
основные экраны не обращаются к массивным endpoints.

## B3 — происхождение записи и выбор материалов

Зависимость: B2.

- Показать существующие author/creator/event_date/confirmation/import provenance
  человеческими подписями, не смешивая дату события и загрузки.
- Не выдавать AI-предложение за подтверждение врача; переиспользовать ImportProvenancePanel.
- Явный выбор по record ID через страницы; показывать общее число выбранных и «Снять выбор».
- Выбор одного пациента → существующие действия «Поделиться» и «Создать случай».
  Проверка актуального доступа перед отправкой обязательна. Backend остаётся источником истины.
- При смене пациента или logout выбор сбрасывается. Скрытая фильтром выбранная запись
  учитывается и доступна в списке выбранного; невозможность доступа удаляет её с объяснением.
- Кнопка «Выбрать страницу» выбирает только текущую страницу, не всю историю.

Приёмка: выбор на двух страницах, смена фильтра и отзыв одной записи не приводят к
передаче другой/недоступной записи; сценарии sharing и мастера не дублируются новой реализацией.

## B4 — ограниченная проверка масштаба

Зависимость: B3.

На отдельной синтетической БД подготовить 100 доступных карточек и историю одного пациента
с 1000 записями и вложениями; также недоступные записи с совпадающими строками.
Проверить число сетевых ответов, размер страницы, отсутствие N+1 по вложениям/счётчикам.
Снять EXPLAIN ANALYZE для списка, поиска и count. Зафиксировать окружение и p50/p95
не менее 30 прогретых запросов. Не объявлять результаты локального стенда production SLA.
Исправить найденные полные выгрузки/N+1; индексы подтверждать планом.
Результат — docs/reviews/history-scale.md и воспроизводимый скрипт с параметром объёма.

## B5 — предупреждение о возможном дубле карточки

Зависимость: B1. Выполнять последовательно с A3 при общих компонентах.

Перед ручным созданием использовать существующий поиск доступных кандидатов:
ФИО + дата рождения, показать совпадения и действия «Открыть» / «Создать отдельную карточку».
Не искать по глобальным недоступным карточкам и не показывать, что такой пациент существует.
Предупреждение не запрещает создание однофамильцев. Ошибка поиска отличается от «совпадений нет»
и позволяет явное продолжение. Проверить существующий UI перед добавлением.
Не создавать merge/link API. Автоматическое слияние не входит в задачу.
Приёмка: одинаковые ФИО с разной датой, полное совпадение, недоступный кандидат, отказ сети.
