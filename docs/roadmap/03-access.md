## C1 — объяснение собственного доступа к записи

Зависимость: B1. Это read-only функция.

- Добавить GET /api/records/{record_id}/access-context через use case/port.
- Доступ только пользователю, уже имеющему право чтения записи; outsider получает 404.
- Ответ перечисляет основания ТЕКУЩЕГО пользователя: source, expires_at,
  прямой разрешённый отправитель, case ID только при праве видеть этот случай.
  Использовать discriminated DTO для видов оснований и существующие enum.
- Несколько независимых оснований показывать отдельно. Истёкшее основание не считать действующим.
- Не раскрывать полный граф пользователей, чужие случаи или обсуждения; доступ к записи
  сам по себе не разрешает читать информацию о чужом членстве.
- В панели записи «Почему мне доступно»: своё основание, полученная передача, материал случая.
  Кнопка перехода существует только для объекта, который пользователь вправе открыть.
- Поле неизвестного/старого source отображать нейтрально, не придумывая владельца.

Приёмка: автор, прямой получатель, два независимых основания, case-only, outsider, истечение
и отзыв. Результат не изменяет UserRecordLink/RecordShare. Совместные записи не клонируются.

## C2 — предпросмотр последствий отзыва

Зависимость: C1.

1. Через существующие правила сформировать read-only расчёт отзыва конкретного sharing request:
   POST /api/share-requests/{request_id}/revoke-preview.
2. Только отправитель, которому уже разрешён revoke; запросы случая не управляются обычным
   endpoint. Они направляют к участникам случая без возможности частичного отзыва материалов.
3. Ответ: scope, affected_record_count, affected_access_count, preserved_access_count,
   expires/updated version marker при наличии; отдельно список прямых получателей запроса.
   Имена и ID скрытых downstream-пользователей НЕ отдавать; по умолчанию только агрегаты.
   Счётчики относятся к выбранной ветке и её последствиям, не раскрывают другие основания.
4. Каскад в preview и revoke использует одну политику/обход, без дублирования алгоритма.
   Изменение состояния и публикация событий происходят только при настоящем revoke.
5. UI объясняет: зависимые передачи отзовутся; независимые права могут сохраниться;
   уже скачанные локальные копии технически не отзываются.
6. Предпросмотр информационный. При подтверждении сервер пересчитывает по свежему состоянию
   в транзакции и возвращает фактический результат. Не обещать неизменность числа участников
   между preview и подтверждением. Повтор revoke безопасен согласно текущему контракту.
7. Если для единой политики требуется рефакторинг, сначала покрыть текущий каскад тестами.
   Нельзя расширять право отправителя на отзыв независимых передач.

Приёмка: A→B→C, альтернативное право B, истёкшее альтернативное право, case source,
повторный revoke, новый downstream между preview/revoke. Preview ничего не отзывает;
после revoke независимые основания живы; повторные read/download/SSE соблюдают отзыв.

## C3 — интерфейс выданных прав и сквозная передача

Зависимость: C2 и A3.

- В существующем sharing UI показать получателя, состояние, срок, разрешённые записи,
  действия отмены/отзыва по lifecycle. Не включать приглашения случая как редактируемые
  обычные запросы.
- Последствия отзыва показать диалогом C2; опасное действие подтверждается.
- Дописать E2E: врач A создаёт запись → пациент принимает разрешённую передачу →
  передаёт врачу B → B читает → A отзывает исходную ветку → B теряет её.
- Второй вариант: у B независимо выдано право, оно сохраняется; членство в случае
  всё равно проверяется отдельно при чтении обсуждения.
- Проверить имена источников и причины отказов без утечки клинического контекста.
- Если исходное подтверждение записи срабатывает при принятии пациентом, сохранить
  действующие правила и provenance; это не новая логика подтверждения.

Приёмка: сценарии выполняются через UI/API без ручной правки БД.
Если для нового аккаунта пациента нужна ещё не реализованная привязка карточки,
использовать существующую легитимную связанную карточку и явно отметить границу теста.
Не считать вопрос привязки решённым этим тестом.

## C4 — проектирование привязки карточки пациента (только ADR)

Зависимость: A1. Результат — docs/decisions/patient-account-linking.md. Реализация не разрешена этим заданием.

Изучить создание PatientPassport и регистрацию. Описать:
- кто вправе инициировать связь и чем подтверждается личность;
- случай существующей личной карточки аккаунта и нескольких врачебных черновых карточек;
- права на записи до/после связи, независимые основания, возможность отзыва;
- ошибочное связывание, аудит и процедура исправления;
- почему ФИО/дата рождения/совпадающий email сами по себе недостаточны;
- 2 возможных процесса, рекомендуемый вариант и точные вопросы владельцу.

Не создавать временный небезопасный endpoint и не добавлять массовое объединение карточек.
Статус done для C4 означает готовый ADR с нерешённым продуктовым выбором, не рабочую привязку.
Отдельная будущая задача на реализацию появится после согласования.
