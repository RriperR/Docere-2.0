## D1 — серверные сессии и отзыв

Зависимости: нет. Выполнять после C3 по основному порядку; самостоятельная задача с Sol high.

- Добавить сущность/таблицу сессии: пользователь, ID, created/expires/last_used,
  revoked_at, причина, семейство refresh и хеш текущего refresh-идентификатора.
  Полные токены/пароли в БД и логах не хранить.
- Новые access/refresh содержат session ID; существующая проверка пользователя сохраняется.
  Каждый авторизованный API, скачивание и перепроверка SSE учитывает отзыв сессии.
- При refresh атомарно заменить refresh-идентификатор, старый становится недействительным.
  Повтор уже использованного refresh отзывает семейство. Параллельный повтор не выдаёт два
  действующих новых refresh.
- Frontend делает refresh через единый single-flight; для вкладок одного браузера
  согласовать обновление через подходящий общий механизм. Не передавать медицинские данные
  в канал координации. При конфликте допустим явный повторный вход, недопустим тихий цикл.
- Добавить список только своих сессий, отзыв одной, выход из текущей и всех сессий.
  В UI показывать время, текущую сессию и недоверенную подпись браузера; не трактовать её
  как доказательство устройства. Не собирать геолокацию.
- Смена пароля и блокировка отзывают все сессии; после смены пароля нужен повторный вход.
- Переход релиза: старые JWT без session ID перестают приниматься, нужен повторный вход.
  Явно описать в release notes. Не оставлять бесконечный legacy обход.
- Logout очищает stores, Blob URL и AI/историю/входящие; не ограничиваться удалением токена.

Приёмка: два устройства, текущий/все logout, чужой session ID, блокировка, смена пароля,
истёкшая сессия, конкурентный refresh на PostgreSQL, replay, отказ сети, прекращение SSE.
Проверить точные HTTP-контракты до UI; миграционный цикл и auth gate обязательны.

## D2 — восстановление пароля

Зависимость: D1.

- Application port отправки письма + SMTP adapter с серверной конфигурацией;
  локально тестовый почтовый приёмник. Секреты только через окружение.
- Request reset отвечает одинаково для существующего/несуществующего email.
  Не раскрывать наличие аккаунта через текст или форму.
- Генерировать криптографически случайный одноразовый token, хранить хеш, TTL по умолчанию
  30 минут. Повторная выдача аннулирует предыдущий; потребление и смена пароля атомарны.
- Письмо содержит ссылку на фиксированный настроенный frontend origin; Host заголовок
  не используется для формирования ссылки. Нет открытого redirect.
- Token не возвращать публичным API и не писать в логи; ссылка одноразовая, reset-страница
  без сторонней аналитики, Referrer-Policy no-referrer. После чтения убрать token из адреса.
- После reset отозвать сессии и другие reset tokens. Не выполнять автоматический login.
- Неверный/просроченный/использованный token — нейтральная ошибка и предложение нового запроса.
- При ненастроенном SMTP обычный вход работает; восстановление явно недоступно.
- Ответ «письмо отправлено» не использовать при известном отказе доставки;
  разрешён нейтральный ответ «Если адрес зарегистрирован, инструкции будут отправлены»
  при надёжно сохранённом намерении отправки.
- Письмо доставлять с ограниченными повторами через существующую инфраструктуру outbox/worker.
  Если для доставки нужен сырой token, не класть его открытым текстом в outbox:
  хранить зашифрованный payload с отдельным серверным ключом, удалить после доставки/истечения.

Приёмка: токен одноразов при двух конкурентных запросах, истечение, повторная выдача,
SMTP error/retry, неизвестный email, блокированный аккаунт не разблокируется reset.
Внешнюю доставку считать непроверенной до получения SMTP-настроек; локальный mail sink проверять.

## D3 — распределённое ограничение запросов

Зависимости: D1 и D2.

- Перенести лимит входа/регистрации/reset в общий Redis adapter через port.
- Атомарный счётчик с TTL; ключи по операции и IP, для login/reset также по хешу
  нормализованного идентификатора. Не хранить plaintext email в ключах.
- Лимиты настраиваемые; сохранить существующий предел login/register до замеров.
- Учитывать forwarded IP только от настроенных доверенных reverse proxies.
- При Redis outage auth mutations возвращают контролируемый 503; уже выданные сессии
  и чтение медицинских данных продолжают проверяться через PostgreSQL.
- 429 имеет Retry-After, одинаковую политику для известных и неизвестных аккаунтов.

Приёмка: два API-инстанса разделяют счётчик, TTL истекает, поддельный forwarded IP не обходит
лимит, Redis outage не пропускает неограниченные попытки, frontend объясняет повтор.

## D4 — отдельная конфигурация стенда

Зависимость: нет; внешний запуск только после D1–D3 и D5–D6.

Подготовить compose override/отдельный файл, пример env БЕЗ секретов и runbook:
- HTTPS на едином входе; Postgres/Redis/MinIO не публикуются наружу.
- Явные secrets, allowed origins/hosts, storage, SMTP, AI toggle, healthchecks.
- API/worker не должны работать с демонстрационными паролями в профиле pilot.
- Миграции запускаются одним шагом до обновления процессов, без seed/reset.
- Хранить предыдущие frontend assets на время перехода, чтобы открытая вкладка могла
  закончить/сохранить работу. После logout старые assets не дают доступ к API.
- Runbook: fresh install, update, failed migration, rollback совместимого приложения,
  smoke, просмотр состояния и логов без медицинских текстов.
- Домен, VPS и TLS credentials не выдумывать. Локальная проверка через тестовый origin;
  недоступные реальные настройки — точный список для владельца.

Приёмка: локальное развёртывание отдельного проекта, health и smoke успешны; существующий
стенд не изменён. Внешнее размещение не выполнять без отдельного поручения.

## D5 — согласованная резервная копия и восстановление

Зависимость: D4.

- Для первого варианта выбрать maintenance window: запрет новых записей, остановка/drain
  всех пишущих API, worker, dispatcher; затем PG dump и snapshot/copy S3.
- Снимок содержит схему/данные, вложения, необходимые метаданные и manifest с версиями,
  временем и проверками целостности. Секреты и ключи восстановления учитывать отдельно.
- При неудаче одного шага backup не помечать полным; предусмотреть безопасный возврат
  сервиса из maintenance. Не удалять предыдущую годную копию.
- Восстановить в НОВЫЕ volumes/БД/bucket отдельного проекта. Скрипт требует явно заданную
  цель и отвергает совпадение с исходной конфигурацией. Не делать restore поверх стенда.
- Проверить количество записей/вложений, SHA-256 выборки, вход, чтение разрешённого,
  запрет чужого, sharing и случаи. Повторная доставка outbox не должна дублировать операции.
- Измерить длительность и фактическое окно потери данных; существующие RPO/RTO —
  цели до эксперимента. Хранение/шифрование backup описать, ключ не класть рядом с копией.

Приёмка: скрипт, runbook и протокол настоящего восстановления синтетического стенда.
Один pg_dump без файлов или копия при продолжающихся записях не выполняют задачу.

## D6 — наблюдаемость фоновых операций

Зависимость: D4; перед завершением проверить вместе с D5.

- Использовать текущие health/admin/audit, не строить вторую административную панель.
- Добавить безопасные показатели: возраст самого старого outbox, expired lease,
  queued/running/failed импорты и AI, длительность/число ошибок провайдера.
- Доступ к диагностике только разрешённой роли; никаких текстов документов, токенов
  и полных ответов провайдера. Метки метрик не содержат patient/file names.
- Для зависшей задачи показать retry/recovery состояние существующего механизма;
  не добавлять ручную SQL-кнопку «сделать успешной».
- Документировать действия при недоступном Redis/worker/AI и критерии восстановления.

Приёмка: остановка worker и брокера на отдельном стенде видна в диагностике,
после возврата pending-работа завершается без дублей; основной импорт не ломается из-за AI.
