# F. Приёмка продукта и ВКР

## F1 — сквозная регрессия и интерфейс

Зависимости: A3, B3, B4, B5, C3, D1–D6, E3.

На отдельном синтетическом стенде использовать пациента, двух врачей и постороннего.
Проверить маршрут:
1. Врач получает роль существующим механизмом.
2. Создаёт/открывает разрешённую карточку, импортирует документы и проверяет предложения.
3. Находит запись в истории, открывает оригинал и видит происхождение.
4. Передаёт выбранное пациенту; пациент — второму врачу в поддерживаемом сценарии.
5. Создаёт случай, приглашает коллегу; тот принимает, открывает документ, отвечает.
6. Координатор сохраняет итог, закрывает, публикует с явной датой события.
7. Отзывает исходную ветку; повторные API/скачивание/SSE соблюдают отзыв.
8. Независимое право сохраняется; оно само по себе не открывает обсуждение случая.
9. Выход/смена пароля очищает UI и прекращает старую сессию.

Матрица: 390/768/1440 px, 200% zoom, длинные ФИО/названия, клавиатура и focus,
пустые состояния, network failure/retry, истечение токена, refresh/reload/back,
новая сборка при открытой вкладке. Не создавать отдельный E2E на каждый цвет/отступ.

Проверить frontend gate, backend gate, цикл миграций на PostgreSQL.
Запускать E2E через frontend/playwright.config.ts с явным PLAYWRIGHT_BASE_URL.
Реальный AI выключен в обычном CI; opt-in прогон отдельно.
Отчёт docs/reviews/pilot-readiness.md: команды, исходные данные, результаты,
скриншоты и точные непроверенные условия. Если внешних SMTP/VPS нет — они не «прошли».

## F2 — исследование с врачами

Ранний проход возможен после A3. Итоговый — после F1.
Агент готовит сценарии и шаблоны; людей не выдумывает и не пишет им без поручения.

Нужно 3–5 врачей, синтетические данные, одинаковый набор задач:
найти документ → импортировать → передать → обсудить → опубликовать → отозвать.
Не объяснять путь заранее; отдельно учитывать вмешательства ведущего.
Зафиксировать успешность, время, ошибки, обращения за помощью и комментарии участников.
Для импорта сравнить ручное заполнение с AI, чередуя порядок и используя сопоставимые документы.
Разделять время ожидания модели и активное время врача.

Результаты:
- docs/research/pilot-protocol.md: инструкция ведущему, начальные условия, задания;
- docs/research/pilot-results-template.md: пустая форма результатов;
- после реальных сессий — обезличенные наблюдения и ранжированный список проблем.
- Критерий продолжения пилота: все критичные утечки/потери текста устранены;
  количественные результаты показываются как наблюдения маленькой выборки.

Статус prepared_external: протокол готов, участники/сессии ожидаются.
Полный done возможен только после реального исследования и разбора результатов.

## F3 — доказательства для ВКР и показ

Зависимость: F1; окончательный раздел исследования — F2 после реальных сессий.

- Обновить docs/THESIS.md, docs/DEMO.md, docs/VALIDATION.md без переписывания архивных PRD.
- Центральная тема: медицинская история и совместная работа с управляемой передачей доступа.
- Отдельные доказательства: cascade/independent grants, проверяемый импорт, collaborative case,
  AI как помощь с обязательной проверкой, восстановление после отказов.
- Демонстрация 7–10 минут: данные подготовлены заранее, действия воспроизводимы,
  резервный сценарий работает без AI-провайдера.
- Тестовые метрики/скриншоты снабдить датой и исходным commit. Цели не записывать как измерения.
- Добавить ограничения: идентификация пациента, размер пилота, внешняя интеграция,
  отсутствие клинической валидации и правовой оценки реальной эксплуатации.
- Не заполнять таблицу руководителя и не публиковать документы без отдельного запроса.

Приёмка: другой человек запускает demo по инструкции без ручной правки БД;
все утверждения о готовности имеют ссылку на тест/отчёт либо помечены как план.
