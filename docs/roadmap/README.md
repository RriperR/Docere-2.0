# Инженерный backlog Docere

Дата подготовки: 12 октября 2026. Проверенная исходная точка: master, commit 76e83e0.
Документ сохраняет инженерный backlog, подготовленный до текущего UX-этапа.
Активный интерфейсный пакет и его статус: [UX-IMPROVEMENT-PLAN.md](../UX-IMPROVEMENT-PLAN.md).
Не начинайте автоматически эксплуатационные задачи из этого списка при работе над продуктовым UX.
Это спецификации задач, не отчёт об их выполнении. Реестр выполнения — [STATUS.md](STATUS.md).

## Цель

Подготовить Docere к самостоятельной проверке несколькими врачами на синтетических данных:
первый вход → история пациента → выбранные материалы → передача доступа →
совместный разбор → публикация → управляемый отзыв.
AI помогает работать с источниками; основные сценарии сохраняются при его отключении.

## Уже реализовано — не создавать повторно

- Карточки пациента отдельно от аккаунтов, записи и вложения, подтверждение и provenance.
- Sharing: принятие, отказ, отмена, сроки, отзыв и сохранение независимых оснований доступа.
- Случаи, запросы мнения, версии итога, публикация, личные черновики, входящие, SSE.
- Общий защищённый просмотр документов.
- Проверяемый импорт ZIP/DICOM/PDF/PNG/JPEG, AI-предложения и личная AI-сводка случая.
- PostgreSQL outbox, Celery/Redis, lease для фоновых AI-заданий.

Наличие функции не означает, что все пользовательские сценарии удобны или готовы к эксплуатации.
Факты о проверках: docs/reviews/2026-10-11-inbox-workflow.md,
docs/reviews/2026-10-11-ai-import.md, docs/reviews/2026-10-12-case-ai.md.

## Рекомендуемый порядок

1. A1 → A2 → A3: начало работы; после этого можно проводить раннее наблюдение F2.
2. B1 → B2 → B3 → B4: история; B5 выполняется после B1.
3. C1 → C2 → C3: объяснение доступа и отзыв. C4 — только проектирование решения.
4. D1 → D2 → D3: аккаунты. D4 → D5 → D6: эксплуатация.
5. E1 → E2 → E3: качество AI. Подготовку E1 можно делать независимо после A1.
6. F1 → F2 → F3: приёмка, пользовательское исследование и ВКР.

D4 можно начать раньше; публичный пилот требует D1–D6.
C4 и E4 имеют отдельные продуктовые ограничения: их нельзя молча превращать в реализацию.
Задачи с незавершёнными зависимостями не начинать в общей рабочей копии.
Внутри крупной задачи разрешены последовательные коммиты с явно указанным оставшимся объёмом.

## Общие обязательные правила

1. Прочитать корневой AGENTS.md. Сохранить слои presentation → application → domain;
   infrastructure реализует ports. SQL не помещать в routers.
2. Не менять правила ролей, подтверждения, sharing и каскадного отзыва ради упрощения UI.
3. Доступ проверяется сервером до выдачи данных и подсчёта результатов.
   Клиентская фильтрация не является авторизацией.
4. Членство в случае и доступ ко всем его материалам обязательны для клинического контекста.
   Независимый доступ к записи не разрешает обход case API.
5. Не объединять пациентов по имени. Не выдавать новые права при поиске, просмотре provenance
   или нажатии на источник AI. Не клонировать медицинские записи для sharing.
6. Новый API: typed DTO, port, repository, response schema и тесты. Ошибки через существующий
   HTTP mapping; незнакомые значения фильтров — 422. Не отдавать трассировки/секреты.
7. Медицинские тексты и документы не сохранять в URL, localStorage, технические логи или
   публичные снимки. Для UI в URL допустимы идентификаторы, состояния, даты и пагинация.
   Свободный медицинский поисковый текст сохранять в памяти текущей сессии интерфейса.
8. Использовать только синтетические данные. Не вызывать seed-demo, demo-reset или down -v
   на существующем стенде. Новые тестовые данные изолировать.
9. Сохранить FastAPI/SQLAlchemy/PostgreSQL/React/TypeScript/Celery/Redis/S3.
   Kafka, новая микросервисная архитектура, OCR-сервис, чат с диагнозами, DICOM-viewer,
   интеграции МИС и полный редизайн в этот пакет не входят.
10. Существующую функцию сначала проверить, затем расширить. Если требование уже выполнено,
    зафиксировать тест/доказательство и не переписывать код.
11. Локальные коммиты непосредственно в master соответствуют указанию владельца в этом чате.
    Push требует отдельного запроса. В параллельной работе коммитит только интегратор.
12. Настройки инфраструктуры и отсутствие доступа к внешним сервисам не выдумывать.
    Подготовить локальную проверку и явно отделить непроверенную внешнюю интеграцию.

## Общая приёмка каждой задачи

- Выполнены все критерии задачи и проверки негативных сценариев.
- Проверен diff на лишние изменения и ослабление ACL.
- Обновлены профильные README/ARCHITECTURE/SECURITY и STATUS.md.
- Указаны реальные команды, результат и commit. Непроведённые проверки названы.
- Один логический результат — отдельный commit; нет push.
- Недостаток бюджета не основание для статуса done: сохранить точную точку продолжения.

Для backend: сначала целевые тесты, затем make test-critical; при существенном изменении
make project-check. Для frontend: npm run test -- <нужные файлы>,
npm run type-check, npm run lint, npm run build из frontend.
Для архитектурных изменений: tests/critical/test_architecture_layers.py.
Для миграций: upgrade/downgrade/upgrade и alembic check только на отдельной тестовой PostgreSQL;
не откатывать пользовательскую БД. Команды запуска окружения брать из docs/VALIDATION.md.
Документальные задачи не требуют полного прогона приложения.
